# T12｜验收与回归清单

**状态：待执行。** 当前仓库处于设计阶段，尚未包含应用代码与实测报告。本文档定义全量功能与非功能需求的复现步骤、通过标准及证据留存规范；业务规则依据[需求规格](REQUIREMENTS.md)，预期 HTTP 状态码、响应字段与错误码依据 [API 契约](API.md)。

## 1. 环境、样例与记录要求

- **隔离测试环境与预置数据：** 使用独立的 MySQL 8.0 测试库，严格按照[操作手册](WORKFLOW.md)从空库执行 `schema.sql` 与 `seed.sql` 初始化。至少准备两名上报人（`R1`、`R2`）、两名评估师（`A1`、`A2`）和一名管理员（`M1`）；预置已启用与已停用的业务资产、完整的 `P0`–`P3` 四档分级规则，以及一段无历史数据干扰的专属创建时间窗口。针对“最后一名管理员并发保护”用例，额外准备第二名管理员（`M2`）。
- **双引擎与并发测试策略：** 优先在未配置 `AI_API_KEY` 的环境下完成离线工单主线验收；随后通过可控的 Mock 模型服务（或兼容端点）分别模拟合法 JSON 响应、字段缺失/越界、HTTP 5xx 错误及读取超时，验证模型调用与本地规则降级。所有外发模型测试均使用人工构造的脱敏故障文本。关键并发抢单与事务回滚用例须基于真实 MySQL 运行集成测试，并通过线程同步屏障（如 `CountDownLatch`）确保并发请求读取同一工单版本号。
- **验收证据留存规范：** 每条用例的验收记录须包含：用例编号、Git 提交哈希、运行环境与 SQL 脚本版本、执行角色、目标事件 ID / 工单号、HTTP 状态码与业务码、数据库核心列前后对比及响应中的 `requestId`。留存精简的 JSON 响应或关键截图即可；归档证据前必须抹除任何密码、令牌、API 密钥及外部模型的原始请求/响应详情。
